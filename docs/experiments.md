# 实验记录与证据分级

## 方法

采用分层故障定位与同路径对照。观察顺序为：虚拟网卡与 DHCP → LAN 请求计数 → 网关服务与规则 → 宿主代理链 → SOCKS5 协商与认证 → TLS/HTTPS → 客机工具 → 目标应用。

本文是从本地结果摘要和操作记录整理的去标识化案例；原始秘密配置、完整日志和截图不公开。实验轮数较少，不具备统计推断或长期稳定性评价能力。

## 出口 A / B 对照

在同一中转节点下，对两个出口各发起独立诊断连接，并在连接存续期间读取宿主代理链，以确认分流条件一致。

| 阶段 | 出口 A | 出口 B |
|---|---|---|
| SOCKS5 方法协商 | 两次约 12.02 秒超时 | 三次正常 |
| 用户名 / 密码认证 | 未进入 | 三次通过 |
| 目标 TCP 连接 | 未进入 | 三次通过 |
| HTTPS | 无成功结果 | example.com 两次 200；api.ipify.org 一次 200 |
| 记录的完整请求耗时 | 超时 | example.com 2.48 秒；api.ipify.org 3.34 秒 |

本地 HTTP CONNECT 返回 200 只表示本地代理接受隧道请求，不证明远端 SOCKS5 入口已响应。入口 A 的超时发生在用户名 / 密码发送之前，因此没有证据说明密码错误。尚未区分入口服务异常、来源限制或特定网络路径问题。

出口 B 替换后，网关通过 HTTPS、DNS A、IPv4 出口比较、唯一入口集合与默认丢弃策略检查。客机随后报告 HTTPS/DNS A 正常、AAAA 无回答、IPv6 TCP 不可达、STUN UDP 无响应；使用者确认目标应用可以收发消息。

## 故障注入历史

更早的出口配置下，曾分别停止代理核心、模拟入口不可达并验证恢复；客机还完成过不依赖 DNS 的 HTTPS“成功—失败—恢复成功”测试。网关重启后的核心、防护及 DNS 持久化也曾通过。

这些结果属于**旧配置的历史证据**。当前出口替换与防护模板修复后，尚未重新进行完整故障注入和冷启动验收，公开版不将其标为当前配置已通过。

## 证据标签

`工具实测`：网关 / 宿主命令实际取得的结果。`使用者回传`：客机工具输出及人工功能确认。`历史证据`：旧配置下完成的测试。`待核实`：缺少独立结果或与当前配置不一致的项目。
